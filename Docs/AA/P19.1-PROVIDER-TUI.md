# P19.1 Provider & Production TUI

## Public Provider Configuration

`providers.json` now exposes only the user-facing model/provider contract:

```json
{
  "$schema": "https://schemas.example.invalid/lingxiagent/providers.schema.json",
  "version": 1,
  "model": "provider/model",
  "providers": {
    "provider": {
      "name": "Provider",
      "adapter": "openai-compatible",
      "options": {
        "baseURL": "https://api.example.com/v1",
        "apiKey": "{env:PROVIDER_API_KEY}"
      },
      "models": {
        "model": {
          "name": "Model",
          "reasoning": true,
          "limit": { "context": 128000, "output": 4096 }
        }
      }
    }
  }
}
```

`apiKey` accepts only `{env:NAME}` or `{vault:REFERENCE}`. Literal credentials are rejected. Resolution order is `LINGXI_<PROVIDER_ID>_API_KEY` → the source the file names → no credential. The prefixed variable is an explicit per-run override for CLI and CI; `{vault:…}` is the only durable store; `{env:NAME}` points into the environment, which a GUI launched from Dock/Finder cannot follow because that process inherits launchd's environment rather than the login shell's. `ProviderCredentialMigration.apply` therefore moves an `{env:NAME}` account into the vault whenever the variable currently resolves — `providers.json` is backed up to `providers.json.bak-pre-credential-migration` first, and an entry whose variable is absent is left exactly as it is rather than rewritten to a pointer that would lose the key. It runs where a product entry point loads the file (`LingXiCoreHost`, `lingxiagent-ops`), never from `CoreHost.start()`: the test binary boots hundreds of hosts and some deliberately read the developer's own data root, so a startup write there rewrites a live profile. The `{env:NAME}` form stays supported for development, CI and command-line use; it is not a GUI's long-term credential source, and no product write path produces it (`updateSecret` only ever emits `{vault:…}`). Account IDs, credential references, endpoint IDs, model profiles, and default-selection records are runtime implementation details and are not encoded in the public file.

The resolver maps `openai-compatible` to Chat Completions, `openai-responses` to Responses, and `anthropic-messages` to the Anthropic Messages wire. Existing P14 internal configuration files are read through a compatibility projection and are emitted in the public format on the next configuration save.

## Production TUI

`LingXiTUI` is a retained ANSI terminal client. It owns terminal rendering state and consumes only `LingXiClient` and protocol projections. It uses alternate-screen/raw input mode, redraws transcript/composer/overlay/status regions, and restores the terminal on exit.

Input routing is strict:

- Lines beginning with `/` enter the structured command registry and never reach the model.
- All other text is a user prompt, including bare words such as `new`.

The registry carries command name, aliases, description, category, argument schema, availability, and handler metadata. The first production command set is limited to existing capabilities: model/provider connection, session creation/resume/history/rename, status/context/compact/perf, mode/permissions, subagents/MCP/skills/plugins/hooks/run inspection, workspace diff, stop, clear, help, and quit.

Pickers use arrow navigation, Enter selection, and Esc cancellation. Provider credentials are masked in the composer. Question and permission requests are rendered as overlays and replied to through the protocol APIs.

The status line reports the active model, project, git branch, execution profile, runtime state, and independent P/E-Core usage. Core computes a stable `ContextCacheProjection` from the existing context and project-cache metrics, including usage, capacity, percentage, state, page movement, paging activity, and compaction generation. The TUI only formats those fields. `/context` prints the complete three-layer projection.
