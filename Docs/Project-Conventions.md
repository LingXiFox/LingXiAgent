# LingXiAgent 2.0 项目规范

适用范围：本仓库 2.0 工作树（分支 `rewrite/2.0`）内的全部代码、插件、文档与脚本。
优先级：当前对话的显式指令 > 本文 > 全局约定。1.x 仓库（`/Volumes/Development/Projects/projects/LingXiAgent`）为只读参考，其规范不自动适用。

## 一、平台与范围

- 唯一目标平台：**macOS / Apple Silicon**。
- 禁止为 Windows、Linux 预先铺设兼容层、条件编译分支、平台抽象替身或 CI job。需要 OS 相关能力时直接写 Darwin 实现，抽象点只到"这一层是平台层"为止，不做第二个实现。
- 禁止在 2.0 阶段继续原生 GUI 开发。前端只保证协议面存在（`Testing-and-Acceptance.md` 的前端契约层），实现按 TUI 优先。
- 1.x 的模块、接口、命名不默认继承。继承任何 1.x 资产时，必须在 `Regression-Cases.md` 或代码注释里指向其证据 ID，说明"为什么这是被验证过的"。

## 二、目录约定

```
Sources/            内核、宿主、协议、平台层、前端（SwiftPM target）
Plugins/            官方插件源码；每个插件一个目录，独立 target
Tests/              单元测试与集成测试
ContractTests/      跨边界契约测试与结构门禁（独立 target，不随产品发布）
Evals/Tasks/        端到端任务定义与 oracle
Evals/Baselines/    基线结果集（真实 trace 产出，禁止手填）
Docs/               设计文档、ADR、验收记录（CC-BY-4.0）
Scripts/            构建、打包、CI 脚本
.tmp/               探针脚本、调试产物、一次性日志（不入库，用完删除）
```

- 不在本阶段新建独立仓库或网站（项目书 §四）。
- `.tmp/` 与 `/tmp` 之外的临时文件不允许出现在工作树。
- 目录内没有内容就留 `.gitkeep`，不预先创建空目录树。

## 三、Core 不膨胀（评审第一判据）

项目书 §五.3：新增需求首先判断是否属于插件能力。评审按下面三步，顺序不可颠倒。

**第 1 步 — 是否落在内核职责白名单内？**
内核只做五件事（项目书 §3.1）：基础 Agent Loop、单会话上下文、压缩/预算/缓存必要能力、执行状态与取消与错误与一致性、插件宿主。
不在白名单内 → 默认是插件，除非能论证"缺了它内核的五条有一条不成立"。

**第 2 步 — 撤销测试。**
任何非核心能力必须能单独关闭且不使基本运行失效。评审时问：把这个插件禁用/卸载后，是否残留失效注册、后台进程、幽灵命令或半态能力？答案是"不确定"就打回。此条对应项目书 §五.4 与 §七「工具真正插件化」。

**第 3 步 — 依赖方向测试。**
内核不得依赖：任何具体模型厂商 SDK、任何工具实现、任何 UI、HTTP 服务实现、SQLite 之外的可再生成依赖。此条由结构门禁自动检查（见 `Testing-and-Acceptance.md` L0），不靠人工自觉。1.x 的 `CoreDependencyGraphGateTests` 直接解析 `Package.swift` 断言核内不可达 UI target，这个手法照搬。

已判定为**内核内容**的少数例外，必须写进本文档并给出理由，不得默默存在。

## 四、依赖与新工具

- 引入任何新的外部依赖（SwiftPM 包、系统服务、命令行工具、 vendored 库）前必须获得主人明确许可，并说明：解决什么问题、为什么标准库和现有能力做不到、维护面多大。
- 能用 Swift 标准库 + Foundation + Darwin 原生 API 解决的，不引第三方。
- 已获准的例外须登记在本节下方，目前清单为空。

## 五、代码约定

- Swift 6 语言模式，严格并发检查开启。跨 actor 边界类型显式 `Sendable`。
- **禁止用固定 `Task.sleep` 驱动时间相关行为**。等待条件用 deadline 轮询或信号；超时语义一律"沉默边界"（silence-bound）而非固定总时长。理由与案例见 `Regression-Cases.md` QA-002、IPC-004。
- 错误必须有名字。禁止把失败压成单个 `.crashed` / `.unknown` 后再无人处理；分类错误码是插件协议的一部分（`Plugin-System-Design.md` 第六章）。
- 不写防御性代码处理不可能发生的内部状态；只在系统边界（IPC 入站、前端入站、磁盘读取、上游 HTTP）做校验。
- 注释、日志、commit message 用英文；文档与评审意见用中文。
- 不新增 feature flag 做向后兼容垫片。分支间不留"暂时关掉"的开关；能力开关由插件启停承担。

## 六、测试约定

- 每个 bug 修复必须绑定一个 `Regression-Cases.md` 的 ID，测试函数名里带该 ID。没有 ID 的回归用例先登记再写测试。
- 测试不得绕过真实边界。1.x 曾出现手工构造 `ToolResult` 直接塞给内核、跳过真实 executor，导致断言验证一个永不可能成立的前提（`Regression-Cases.md` QA-001）。2.0 的截断、归档、投影都发生在被调用方一侧，测试必须跨这条边界。
- 默认零真实网络、零真实凭据。需要真实上游的用例一律 env 门禁，且必须在 CI 的独立 job 而非 PR 门禁里。
- 断言终态时**同时钉 cause 不只钉 status**。"取消后状态是 cancelled"不够，还要断言没有伪造出 provider 故障（LOOP-006）。

## 七、Git 与提交

- 分支：`rewrite/2.0` 为主线；单次重构超过 3 个文件先给一句话计划。
- Commit message 用英文，写"为什么"而不是"改了什么"。1.x 历史里带 `[skip ci]` 的提交是纯文档与测试重构，2.0 沿用此约定，但**代码变更不得加 `[skip ci]`**。
- 不使用 `--no-verify` 跳过 hook。hook 失败要查根因。
- 不 amend 已推送的提交。

## 八、许可与版权登记

- 三份 LICENSE 与 `LICENSE-MATRIX.md` 沿用 1.x 的法律文本，**矩阵内容对 2.0 已过期**：表中列出的 target 路径在 2.0 工作树中不存在。首个 SwiftPM target 建立时必须重写矩阵，只保留实际存在的 target。
- 轨道选择：内核/宿主/协议/平台层 → LCSAL-1.1；前端与插件（含官方插件）→ PolyForm Noncommercial 1.0.0。其他轨道需与主人讨论后再合并。
- 新增 target 未登记矩阵视为构建失败，不是评审意见。
- `Docs/` 为 CC-BY-4.0；`Evals/Tasks`、`Evals/Baselines` 尽量 CC0。

## 九、安全红线

1. **凭据不可碰**：不读取 `~/.ssh`、`~/.aws`、`.env` 等凭据内容；不提交密钥。
2. **子进程环境默认白名单**：任何被拉起的进程（插件、sidecar、工具）的环境变量必须是严格 allow-list，而不是"从继承环境里过滤掉敏感项"。必须有一条 sentinel 值探针测试证明 passphrase 与 `*_API_KEY` 进不了子进程，同时 `PATH`/`HOME` 仍存活。1.x 的 `CredentialNonLeakageTripwireTests` 与 `EnvironmentSanitizer` 是被验证过的做法，缺陷在于 MCP 侧当时"这次先不动"，成了遗留泄漏点（`Regression-Cases.md` PLG-008）。
3. **破坏先备份**：删除、覆盖、迁移前先备份，主人验收通过才删备份。禁止对变量拼接路径执行 `rm -rf`。可再生成目录（`.build/`、`dist/`、`node_modules/`、`.tmp/` 等）除外。
4. **线上先许可**：任何可能重启、停止、降级或影响线上服务的操作，执行前必须取得明确许可。
5. **不承诺做不到的隔离**：1.x 插件 SDK 的 README 已诚实说明**无内核级沙箱**。2.0 在未真正把 macOS sandbox 机制接到插件进程之前，文档与插件 manifest 不得出现"沙箱隔离"表述，只能说进程隔离与权限声明。

## 十、阶段推进门禁

不并行铺所有工作。进入下一阶段前必须满足：

| 进入 | 前置 |
|---|---|
| 阶段 1 | 本文与 `Kernel-Design.md` 定稿；待决项 1、3（macOS 最低版本、LICENSE 矩阵）已解决 |
| 阶段 2 | 阶段 1 验收通过：空内核可启动、单上下文连续、取消与恢复的回归用例全绿 |
| 阶段 3 | 首个 Provider 插件与首个基础任务插件跑通，且未修改内核代码 |
| 阶段 4 | 插件异常隔离与启停撤销的验收（项目书 §七 三条）通过 |
| 阶段 5 | TUI 达到"可长期使用"判定；缓存统计能出自真实请求的数据 |

各阶段的判定方式在 `Testing-and-Acceptance.md`。

## 十一、文档维护

- 决策记录以 ADR 形式追加在 `Docs/Decisions/`，一个决定一个文件，包含：背景、选项、选择、代价、可逆性。改变已有决定要新开文件并指明取代关系，不原地改写。
- 文档只在设计变更时更新。发现文档与代码不一致，先判定谁错了，再改对应一方；不允许"以代码为准"放任过期文档。
- `Regression-Cases.md` 是活文档：每修一个 bug 追加一条，每废弃一条架构标注废弃原因，不直接删行。
