# E-Core Heat 基础设施 Phase 0.5 观测期分析报告 (Observation Report)

## 1. 观测期概述与核心纪律

### 1.1 阶段定位
根据系统演进规范，在完成 Phase 0 与 Phase 0.1 后，系统进入 **Phase 0.5 Observation Period（实采观测期）**。本阶段的核心目标是：
**使用真实 LingXiAgent 生产工作负载收集 E-Core Heat 访问数据，分析其真实统计分布，为未来 Hot/Cold 决策提供坚实、客观的数据支撑。**

### 1.2 纪律红线执行情况
本阶段严格遵守三大纪律与八项注意，坚决贯彻“以臆想业务为耻，以人类确认为荣；以假装理解为耻，以诚实无知为荣”：
* **0 算法与策略变更**：未修改任何 Heat 累加器算法、衰减半衰期、事件权重与冷热分区策略；
* **0 物理文件迁移**：绝未启用任何物理文件的冷热搬迁或目录归档；
* **0 外部重型依赖**：未引入任何 ML、Embedding、自学习模型或外部统计服务；
* **0 侵入主链路**：P-Core（Active Memory / Turn Context）、`ContextProjection`、`context_recall`、Prefix Cache 行为 100% 保持原样；
* **全流程只读、旁路与 Fail-Open**：所有统计指标均基于离线扫描或按需只读快照计算，绝不在前台每次 recall 时引入排序或全量扫描。

## 4. 关键问题深入解答与分析

### 4.1 当前 Heat 分布长什么样？
* **超长沉寂的“低底噪”分布**：
  由于物理磁盘上的 207 个存量对象生成于数十至上百小时之前（历史真实开发任务），在 $T_{half} = 3600\text{s}$（1小时）的 Decayed Accumulator 作用下，未被访问的对象热度已平滑衰减至 $10^{-22} \sim 10^{-8}$ 数量级。
* **无数值溢出或脏数据**：
  全量 207 个对象的热度分值均为严格有限的非负浮点数，MAD == $8.98 \times 10^{-22}$，未产生任何 NaN、除零或溢出异常。

### 4.2 是否明显重尾？
从真实数据分析，呈现出两个层次的特征：
1. **存储与召回的宏观极端偏态**：
   **100% 的生成对象在存储后未被再次 recall**。这表明在当前 Agent 工作模式下，大部分工具输出在对象化存入 E-Core 之后，模型倾向于直接基于当时的 Active Prompt 上下文完成决策，极少需要回溯召回历史长文本。
2. **微观访问频次的重尾特征暂未显现**：
   由于真实 recall 事件样本数目前为 0，尚无法从真实事件层面观测到“Top 5% 对象贡献 80% 访问”的访问级重尾现象。

### 4.3 哪个 Percentile 区间覆盖了大部分真实 recall？
* **实事求是结论**：由于当前真实生产数据中的 recall 样本为 0，**无法仅凭真实数据划定覆盖大部分 recall 的百分位区间**。
* **基准仿真参考**：在经典高偏态仿真中，Top 5% ~ Top 10% 即可覆盖 90% 以上的 recall；但在真实工作负载证明之前，绝对不能将此仿真值直接套用为生产配置。

### 4.4 storedWeight 是否需要未来调整？
* **当前表现**：
  当前 `storedWeight = 1.0`。得益于 Phase 0 中引入的统计学稳健公式——中点百分位等级（Midpoint Percentile Rank）：
  $$\text{Rank} = \frac{\text{count}(x < v) + 0.5 \times \text{count}(x == v)}{N}$$
  当 100% 对象均处于相同的基准热度时，它们的所有 Percentile 均被精准定位于 **0.50 (P50)**，**完全没有虚高霸占 P80/P90 高分位**。
* **未来调整建议**：
  若未来长期观测表明绝大多数对象（例如 > 90%）都不会被召回，可考虑在 Phase 1 将 `storedWeight` 适当调低至 `0.2 ~ 0.5`，而保持 `recalledWeight = 2.0` 不变。这样可以进一步扩大“被召回对象”与“未召回对象”的信噪比差距。

### 4.5 1小时 half-life 是否表现合理？
* **时间尺度匹配**：
  单会话内的多轮复杂对话通常在 10 分钟到 2 小时之间完成。1 小时半衰期使对象在 2 小时内仍保留约 25% 的余温，对于会话内的连续关联调用具备良好的“保鲜期”；
* **跨会话沉寂衰减良好**：
  对于数天前结束的历史会话，对象热度自然衰减至近乎 0，不会污染后续会话的全局高热统计，表现符合预期，目前无须调整。

### 4.6 下一阶段是否已经有足够数据进入 Hot/Cold Phase 1？
* **技术结论直给：当前样本量严重不足！**
* **理由**：
  虽然磁盘上存在 207 个对象元数据，但 `ecore-events.jsonl` 是刚上线的埋点，真实会话中的召回事件目前为 0。
* **主见与拒绝妥协**：
  **严禁根据预设结论强行推荐 Top 20% Hot，严禁在无真实召回数据时强行推进 Phase 1。**
  必须老老实实保持在 **Phase 0.5 Observation Period**，让带有 Phase 0 遥测基础设施的 LingXiAgent 在主人后续的日常编码任务中持续运行，积累至少数十次真实 `context_recall` 事件后再做研判。

## 5. 建议与下一步行动

1. **维持当前版本静默观测**：
   代码已具备完全旁路、Fail-Open 的事件追加与导出能力，保持当前配置在日常任务中自然累积数据；
2. **等待数据成熟指标**：
   建议当累计满足以下条件时，重新运行导出并召开 Phase 1 评审：
   * 真实会话数 $\ge 20$ 个；
   * 真实 E-Core 存储事件 $\ge 50$ 次；
   * 真实 E-Core 召回事件 $\ge 20$ 次。
3. **保持解耦**：
   无论何时推进 Phase 1，始终遵守 P-Core 与 E-Core 的彻底解耦红线，不联动 L1/L2，不干扰 Prefix Cache。
