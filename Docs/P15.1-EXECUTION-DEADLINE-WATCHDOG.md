# P15.1 Execution Deadline & Watchdog

## Runtime invariant

任何可能阻塞 AgentRun 的外部执行都必须最终进入 `success`、`failure`、`timedOut`、`idleTimedOut` 或 `cancelled`。Provider、Tool、Shell/Process、MCP 和 Subagent 不允许永久 pending。

## Deadline model

`ExecutionDeadlinePolicy` 是 Core Runtime 的统一入口。Runtime policy 提供 category default 和 maximum；调用点可以请求更短的 timeout；parent deadline 会继续 clamp。effective timeout 为三者最小值。没有 `nil`、`0`、`Int.max` 或 infinity 形式的生产无限 timeout。

`ExecutionDeadline` 使用 `ContinuousClock.Instant`，因此 elapsed/deadline 不受系统 wall clock 调整影响。`.now`/Date 仍只用于既有持久化和展示时间戳。

## Timeout categories

当前保持少量稳定分类：

| Category | Default |
| --- | ---: |
| `quickFilesystem` | 10s |
| `search` | 30s |
| `foregroundShell` | 60s |
| `buildTest` | 300s |
| `mcp` | 60s |
| `provider` | 120s, idle 45s |
| `subagent` | 600s |
| `agentRun` | 1800s |

所有值都受 `maximumSeconds` 限制。模型或 profile 提供的 timeout 只能被 clamp，不会获得无限执行权。

## Watchdog

`ExecutionWatchdog` 只负责 timer、deadline expiration、idle expiration、取消和 terminal diagnostics。它使用 structured concurrency 与可取消 timer，不做 busy polling，也不做 retry、planning、fallback、workflow scheduling 或 Provider failover。

Provider stream 每收到一个 event 会刷新 idle watchdog。idle 到期会取消 source、发出 `.failed(CoreError(.idleTimedOut))` 并 finish stream；overall 到期使用 `.commandTimedOut`。正常 Provider event 和 Golden projection 不变。

## Cancellation propagation

Root AgentRun 的 Task cancellation 会经过 SessionRuntime 传递到 Provider stream、Tool execution、MCP call 和 child AgentRun。单个 Tool 的 deadline 只取消该 Tool operation，不取消 root lane。Session shutdown 会取消并等待 turn task；Core shutdown 会等待 AgentRuntime 和 owned process store 清理。

## Tool and mutation semantics

ToolRuntime 在所有 builtin/tool executor 外层施加 category deadline。只读 read/search timeout 是普通 `ToolResult`，不会自动 retry；Agent loop 可以继续消费结果。Shell timeout 保留 bounded stdout/stderr。

Mutation timeout/cancel 不能伪装成确定失败。`ToolResult` 使用 `outcome = timedOut`，并在 metadata 标记 `executionState=unknown`、`verificationRequired=true`，错误码为 `executionStateUnknown`（内层命令 timeout 仍保留 timedOut outcome）。Runtime 不执行 blind retry；后续确认由模型通过 read/git status/diff 决定。

## Process cleanup

Foreground process 使用现有 bounded output ring buffer；timeout/cancel 先 terminate，250ms grace 后 force kill，并关闭 readability handlers、drain bounded output、等待 termination。background `process start` 立即返回 `ProcessStatus`，后续用 poll/input/stop 管理；owned process 有一小时 maximum lifetime，并由 Core shutdown stop/wait 清理。

当前 macOS backend 能可靠终止直接 managed process；复杂跨 shell 的 descendants/process-group 隔离仍受 Foundation Process API 限制，属于后续增强，不把它伪装成已完全解决。

## MCP

MCP HTTP request 使用 request timeout 并保留 cancellation；stdio request 复用 managed process deadline。`initialize`/`tools/list`/`tools/call`/resource/prompt 等最终都经 transport 的 bounded request 或 ToolRuntime watchdog。`MCPConnectionManager` 记录 `healthy`、`degraded`、`unavailable`，一次 timeout 不会永久禁用 server，也不在本阶段自动 failover/reconnect。

## Provider

Provider request 使用 `ModelRequest.overallTimeoutSeconds` 设置 URL request timeout；transport 将 URL timeout 映射为 typed timeout，将其他连接中断映射为 `transportLost`。ModelGateway 对 connection/setup 以及 returned stream 统一加 watchdog。Provider timeout 不自动换 Provider、换 Model、retry 或 fallback。

## Subagent

Child AgentRun 有独立 deadline；显式 profile timeout 可以缩短 category default，但会被 Core maximum 和 parent remaining clamp。child deadline 到期后 child terminal 为 `timedOut`，父 Agent 收到 `SubagentResult` 后继续，Runtime 不替父模型决定重试或重 spawn。

## Configuration and persistence

生产 truth 是 typed `CoreConfiguration.runtime.execution` JSON。字段拥有 defaults，JSON Schema 提供正值校验，Runtime policy 再执行 maximum clamp；environment 只用于 test/debug，不是 timeout truth。既有 `AgentRunStatus.timedOut`、terminal AgentRun/Result persistence 和 restart recovery contract 保持不变。

## Known limitations

- 现有 `AsyncThrowingStream` 上游如果违反 cancellation contract，Swift task 本身无法强制修复其内部阻塞；watchdog 会先 terminalize 下游并发出诊断。
- Process group descendants 的完全隔离需要更底层 process launcher；当前有 TERM/force-kill direct-process fallback。
- Timeout 后 retry、Provider fallback、复杂 MCP failover、recovery-required run 的自动恢复留给后续阶段。
