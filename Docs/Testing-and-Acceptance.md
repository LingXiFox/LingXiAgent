# LingXiAgent 2.0 测试与验收策略

依据：项目书 §五.5–6（质量优先、真实验证）、§六（阶段交付物）、§七（完成标准）。
本文回答一个问题：**每条完成标准用什么证据判定**。答案是"人工看过觉得没问题"的一律不算通过。

## 一、分层门禁

| 层 | 内容 | 时长预算 | 进 PR 门禁 | 需要子进程 | 需要网络 |
|---|---|---|---|---|---|
| L0 结构 | 依赖方向、协议类型无孤儿、能力声明无默认值、许可矩阵无漂移 | < 5s | 是（永久红=不可发布） | 否 | 否 |
| L1 单元 | 上下文投影/切片/范围、读共享波次、批次配对、deadline 语义、SSE 与事件归一、错误分类 | < 30s | 是 | 否 | 否 |
| L2 契约 | 假 Provider + 假工具 + **真 Plugin Host 加载故障插件 dylib**；前端 wire 形状；凭据不泄漏 tripwire | < 90s | 是 | 是（本机） | 否 |
| L3 端到端任务 | 真宿主 + 真工具 + 真子进程插件跑完整任务，oracle 真跑 Agent | 分钟级 | 分块跑，非每 PR | 是 | 否（脚本 Provider） |
| L4 缓存与真实上游 | VCR 金标准回放、真实凭据 smoke、缓存复用率与成本/延迟统计 | 十分钟内 | 否，周期/dispatch | 是 | 是（env 门禁） |

L2 是项目书"插件异常"验收的家，也是 2.0 相对 1.x 最重要的一层补强。

**默认零真实网络、零真实凭据**。需要真实上游的用例必须 env 门禁（沿用 1.x 的做法：`LINGXI_ENABLE_REAL_PROVIDER_TESTS`、`LINGXI_RUN_REAL_PROVIDER_SMOKE`、`LINGXI_VCR_MODE` 等），并在 CI 独立 job 里跑；CI 强制隔离 `HOME` 与数据目录。

## 二、L0 结构门禁细则

这四条直接决定 2.0 能不能守住"最小内核"，必须自动检查而非靠评审自觉：

1. **依赖方向**：解析 `Package.swift`，断言内核 target 不可达任何 UI/前端 target、不可达任何 Provider 或工具实现 target、不可达厂商 SDK。1.x 的 `CoreDependencyGraphGateTests` 手法照搬。
2. **无孤儿契约类型**：协议 target 里每个公开类型必须有生产者或消费者，违反即失败，带显式 allow-list。这是防止 2.0 重演"hook 全套类型都在但生产代码零调用方"的唯一有效手段（PLG-006）。
3. **能力不得继承**：能力与权限声明结构无默认参数，不显式声明就不通过（PLG-009）。
4. **许可矩阵一致**：`Package.swift` 里的 target 集合必须与 `LICENSE-MATRIX.md` 完全对应。注意当前矩阵内容是 1.x 的清单，2.0 首个 target 建立时必须先重写矩阵（`Project-Conventions.md` 第八章）。

## 三、测试替身

直接继承 1.x 的六件（都是被大量测试压过的）：

| 替身 | 用途 | 备注 |
|---|---|---|
| `withTestCoreHost` 式夹具 | 起真实宿主、双路径 shutdown、零孤儿任务 | 成功与抛错两条路径都要清理 |
| 脚本化假 Provider（`ScriptedFakeProvider` / `ControllableFakeProvider`） | 喂入预定义 `[[ModelEvent]]` 序列 | L1/L3 的主力，零网络亚秒级 |
| 故障注入传输 | 断连、丢帧、重放失效、代际失配 | 1.x 的 643 行 `FaultInjectingTransport` 是 transport 级；2.0 还需要**进程级**注入，见下方第三件 |
| loopback 假服务 | 假 Provider HTTP、假 MCP HTTP、假 LSP 传输 | 纯裸 socket、无第三方依赖 |
| 假 PTY | 终端行为测试 | 阶段 4 TUI 用 |
| 跨平台 `LockedState` | 替代 Apple-only 锁 | 2.0 单机 macOS 也保留，避免测试与平台纠缠 |

**必须新增的三件**：

- **注入式时钟**。1.x 未找到假时钟，靠 `.serialized` + deadline 轮询替代固定 sleep，代价是 23 个测试文件仍与调度纠缠（QA-002）。2.0 的三类超时、冷却窗口、退避序列、水位触发都要能在虚拟时钟上确定性地跑。
- **真实假工具**。禁止手工构造工具结果直接塞给内核。1.x 出现过这种测试手法，导致断言验证一个永不可能成立的前提（QA-001）——截断、归档、投影都发生在被调用方一侧，测试必须跨这条边界。假工具必须是"被真实执行引擎执行的真实实现"。
- **故障插件 dylib**。运行模型改成 C ABI + Plugin Host 之后，故障注入必须落在**进程级**：用一个真实的测试插件动态库被真 Host 加载，然后让它分别 ① 段错误退出、② 挂死沉默、③ 返回非法帧/非法结构体尺寸、④ 对调用无应答、⑤ 越出授予权限访问、⑥ 在环境中读到宿主凭据。每种一条断言，且断言 Core 与 TUI 进程存活、受影响的那个 Run 拿到 `Plugin-System-Design.md` 第六章分类表内的错误码。这一层是项目书"故障真正隔离"的家。

跨平台子进程替身（`PortableFixture`）不继承：2.0 单平台，不需要。

## 四、L3 端到端任务验证

1.x 的 `Evals/` 是空壳，**不可作为"真实验证"的证据**（E-11）：其 Runner 从不启动 Agent，只跑 `bash oracle.sh` 然后按 `success ? 2 : 0` 伪造 toolCallCount、llmTurn、tokens、cost；9 个 oracle 全是 `swift test --filter` 或 `git log --grep`，且 `exit 0` 无条件兜底，导致 oracle 永不误红；`Evals/Baselines/*/summary.json` 的 p50 与成本即由这套算式产出，且 Evals 未接入 CI。

**2.0 的 L3 必须真跑 Agent**（QA-003）。继承的只有判据设计：

- 任务定义 `task.json`：`prompt` / `maxSteps` / `timeout` / `oracle`。
- oracle 必须是**对真实世界副作用的核查**，不是"某测试变绿"：git diff 范围、目标文件字节、命令退出码、必须出现/不得出现的内容。
- **非劣性四规则**：零翻转（原来过的任务不得变红，硬失败）、p50 耗时/工具数/成本劣化 ≤ 5%、钉住模型与协议版本、离线回放与真凭据分轨（QA-004）。
- 不得弱化 oracle。基线变动必须显式批准，不能悄悄改期望值。

1.x 真正有效的端到端手法要继承三种：
1. **八阶段脚本 Provider 拟真**（零网络、亚秒）：冷启动 → 大输出入归档 → 全量发送 → 投影 → 按 offset 回读命中内嵌锚点字符串 → 经济压缩 → 债务偿还，逐阶段断言模型回包里的 `[ACK:TURNn]` 与调度状态。2.0 版本改为：冷启动 → 大输出截断 + 引用行 → 显式回读命中锚点 → 水位压缩 → 因果批次保留。
2. **VCR 金标准**：见 `Provider-Plugin-Contract.md` 第七章。
3. **进程级端到端**：真宿主 + typed client，覆盖 wire 形状、跨重连的待答交互、真实 git worktree。

验收记录写法继承 1.x `Docs/Validation/` 的**双向验证**：给实测数字 + trace 严格顺序 + 反例（把 bug 重新注入后测试必须变红）。只给"测试通过"不算验收。

## 五、L4 缓存与成本统计

对应项目书 §七第 7 条"缓存优化有证据"。判定口径（`Kernel-Design.md` 第十章的度量侧）：

1. 数据必须来自**真实请求**：上游 usage + 客户端结构指纹双轨，两者不一致时分别上报，不得合成一个数。
2. 上报项至少含：可比请求数、前缀稳定性（单 hash / bust 次数 / appendOnly 违规 / epoch 变化）、`cacheReadTokens` 与分母、块粒度量化说明、p50/p95 首字节延迟与总耗时、按模型目录折算成本。
3. 禁止把 VCR 合成数据当实测（1.x 的恒 4000 常量就是这类污染源，QA-009）。
4. 基线文件记录 protocol / commit / platform，跨版本比较前必须先确认这三项一致。
5. 命中率下降但任务质量上升时，**质量优先**（项目书 §3.4）；这条要写成评审规则而非口号——出现这种权衡时开 ADR 记录取舍。

## 六、TUI 验收（阶段 4）

项目书把 TUI 定为正式界面，质量以真实使用体验为准。**渲染载体与依赖尚未选定**：Phase 0.1 决策第 3 条明确暂不迁移 1.x vendored 的 OpenTUI 动态库，TUI 的依赖与渲染方案在后续阶段独立验证（那是外部依赖，需单独审批）。下表的判定项与渲染选型无关，无论用哪条实现路径都要过。

可判定项：

| 项 | 判定方式 |
|---|---|
| 流式输出稳定 | 长输出 + 尺寸变化下无撕裂、无错位、无卡顿累积；已投递增量与取消后迟到增量行为符合 LOOP-017 |
| 输入可靠 | 中文/组合字符/粘贴多行/快捷键不误触；IME 行为在真实终端验证 |
| Markdown 与代码展示 | 表格、嵌套列表、长代码块、语法高亮在 80/120/200 列下的排版实测截图存档 |
| 工具过程呈现 | 批次内每个调用的状态、耗时、失败原因可见；取消与恢复信息明确 |
| 会话与模型管理 | 列表、切换、重命名、goal 字段在各类操作后不被清空（STORE-006） |
| 插件管理入口 | 启停、版本、权限、故障状态可见可操作（项目书 §3.5） |
| 长时间任务 | 小时级任务内存不无界增长，事件日志有界，前端不积压 |
| Core 与 TUI 解耦 | Core 崩溃时 TUI 给出明确诊断而非随之退出；重启后能恢复会话（D4） |

1.x 的相关测试**基本不可继承**：`Sources/LingXiTUI` 6757 行只有渲染层与按键绑定测试，名为 TUI 的其实是 SwiftUI 测试；无 TUI 端到端。唯一值得继承的是 `TerminalEmulatorTests` 的 5 条纯 ANSI 语义断言。阶段 4 需自建假 PTY 驱动的 TUI 端到端层。

## 七、项目书第七章完成标准 → 证据映射

| 完成标准 | 判定证据 | 层级 |
|---|---|---|
| 空内核可启动 | 无任何 Provider 插件时启动、状态展示、引导配置成功；结构门禁证明内核无厂商依赖 | L0 + L3 |
| Provider 真正插件化 | 不改内核一行代码、不重编内核，安装/切换 Provider 插件完成对话；用两个不同 wire family 各证一次 | L3 |
| 工具真正插件化 | 装基础任务插件完成真实编程任务；禁用后四条件零残留（`Plugin-System-Design.md` 第五章） | L3 + L2 |
| Hook 真正有效 | 三类各证一次：`transform` 改写一次参数、`security` 否决一次危险操作、**`security` 类 Hook 故障时判定为拒绝（fail-closed）**；且 L0 无孤儿类型门禁通过 | L1 + L2 + L0 |
| 故障真正隔离 | 真 Plugin Host 加载故障插件 dylib，六种**进程级**异常下内核与前端进程存活、错误落在分类表内、受影响 Run 走恢复矩阵 | L2 |
| 会话与上下文可靠 | 崩溃恢复矩阵逐行验证；`Regression-Cases.md` LOOP/CTX 组全绿 | L1 + L3 |
| 缓存优化有证据 | L4 报告出自真实请求，双轨数据齐全 | L4 |
| TUI 可长期使用 | 第六章八项实测记录，含反例验证 | L3 + 人工 |
| 交付可维护 | 官方插件带 README/LICENSE/验收清单通过；开发者文档能指导第三方写出可加载插件；L0–L2 作为回归基线存在 | 文档 + L0–L2 |

## 八、CI 形态

单平台单流水线：build → L0/L1/L2 快检 → L3 分块。机制继承 1.x 的分块脚本，内容不继承其跨平台部分：

- 按 suite 数分块（1.x 用 12 块），每块独立 watchdog + **一次隔离重试**（隔离重试用于确认是否 flake，重试仍失败才算真失败）。
- 每块落 `--event-stream-output-path`，这样进程被 kill 后仍能指名卡住的那个用例。
- "发现的用例数为 0"即失败（防止过滤器写错导致整块空跑变绿）。
- 被 skip 的 suite 计入"已报告"，不允许静默消失。
- flake 记录进 `Regression-Cases.md` 的 QA 组并限期处理；靠 `[skip ci]` 或长期 retry 掩盖 flake 是禁止行为。

## 九、当前缺口（诚实记录）

1. 阶段 4 的 TUI 端到端层在 1.x 完全没有对应资产，工作量容易被低估。
2. 真实 Provider 的金标准 cassette 目前近乎为零，L4 需要到阶段 5 才有历史可比；应尽早开始攒，不等到发布前。
3. 1.x 的"缓存命中率"只有一处真实 smoke 数据（43 个可比请求），样本远不足以支撑趋势判断，2.0 的 L4 要把取样变成例行而非一次性。
4. **C ABI 导出与动态加载在 1.x 无先例**：全仓 `@_cdecl` 零命中，唯一的运行时 `dlopen` 是 `OpenTUIShim` 的 C 封装，且它没有结构体 version/size 字段、错误用 `static error_message[256]`、加载时不校验签名与来源。2.0 的插件 ABI 是仓库里第一次做这件事，阶段 2 必须专门验证三件事：尺寸协商与前向兼容、符号缺失的可读失败、插件不重复嵌入 Swift 运行时。
